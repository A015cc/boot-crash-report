# boot-crash-report

开机时自动读一遍 Windows 的崩溃记录，直接告诉你**上次为什么崩的**。

纯 PowerShell 5.1，**只读、不需要管理员权限、无第三方依赖**。

> 脚本的输出和注释都是中文。README 也用中文写 —— 因为输出是中文的，
> 英文读者拿到的报告也读不了。有需要可以提 issue。

---

## 它解决什么问题

Windows 自带的事件查看器和可靠性监视器都只告诉你"崩溃了"。要真正搞清楚**崩在
什么时刻、停止码是什么、是蓝屏还是硬挂死、崩溃之前系统里变了什么**，你得自己从
几千条日志里翻。

而且有两类崩溃极容易被混为一谈：

| | 蓝屏 (BSOD) | 硬挂死 |
|---|---|---|
| 现象 | 蓝屏 + 停止码，自动重启 | 黑屏 / 画面卡死 / 键鼠无反应，只能强制重启 |
| 转储 | 有 | **通常没有** |
| 事件 | `BugCheck` 1001 | 只有 `Kernel-Power` 41 |
| 能自动分析吗 | 能 | **不能 —— 现场根本没留下来** |

第二类是最难查的：系统在写出任何东西之前就失去了响应，所以事后什么线索都没有。
本工具会**把这两类明确区分开**，而不是笼统地说"系统崩溃过"。

## 安装

```powershell
git clone https://github.com/<you>/boot-crash-report.git
cd boot-crash-report
.\install.ps1
```

`install.ps1` 会在你的**启动文件夹**里放一个快捷方式（不需要管理员权限，不写注册
表，不建计划任务）。卸载：

```powershell
.\install.ps1 -Uninstall
```

想先看一眼效果，直接双击 `run.cmd`，不用重启。

窗口 **120 秒后自动关闭**，按任意键立即关闭。想跳过等待（例如在自动化里调用）：

```powershell
.\boot-crash-report.ps1 -NoWait
# 或
$env:CRASH_REPORT_NOWAIT = '1'
```

## 它读什么（全部不需要管理员权限）

| 来源 | 拿到什么 |
|---|---|
| `System` 日志 `Kernel-Power` 41 | 非正常关机 —— **包括没留下转储的硬挂死** |
| `System` 日志 `EventLog` 6008 | 上一次意外关机的**准确时刻** |
| `System` 日志 `WER-SystemErrorReporting` 1001 | 蓝屏停止码 + 4 个参数 + 转储路径 |
| `WER\ReportArchive\Kernel_*` | 显卡 / 内核超时报告（TDR） |
| `C:\Windows\INF\setupapi.dev.log` | 驱动与设备的真实安装时刻 |
| `WindowsUpdateClient/Operational` | 系统更新成功 / 失败 |

**崩溃时刻取自 6008 的文本**，而不是 41 的时间戳 —— 因为 41 记录的是**重启时刻**，
不是崩溃时刻，两者经常差十几分钟。

以下内容需要提权，本工具**不读**（也读不到）：`.dmp` 文件内容、
`WER\ReportArchive\*` 里的 `Report.wer` 正文、`LiveKernelReports`。

## 设计上值得说的两点

### 1. "例行"的判据必须视场景而定，而且可能是相反的

系统日志里绝大多数错误是**背景噪音**：某台机器上 Google 更新服务启动失败 122 次、
DCOM 超时 50 次、iSCSI 重连 38 次 —— 全都与崩溃无关。如果不过滤，真信号会被淹没。

但"什么算例行"在两个场景下判据**恰好相反**：

- **驱动变更**：在崩溃窗口**内**跨 ≥3 天重复 → 例行。
  （有些设备真的每次开机都重装，那是它的正常行为。）
- **错误日志**：在崩溃窗口**之外**跨 ≥3 天重复 → 才是背景噪音。

错误扫描如果偷懒沿用第一个判据，**一个正在恶化的硬件故障连报三天就会被当成"例行"
吞掉** —— 越是持续性的问题越容易被过滤掉。这是本项目里最容易写错的一处。

### 2. 第二层扫描不预设事件 ID

与其维护一张"我关心的错误 ID"清单，不如把所有 ERROR/CRITICAL 拉出来，用统计方法
自动滤背景噪音。这样**新的失效模式不需要作者提前想到就会冒出来** —— 磁盘报错、
内存错误、热告警都一样。

实测：514 条错误 → 滤掉 11 类背景噪音 → 8 类进报告。不是洪水。

## 已知限制

诚实地说清楚它做不到什么：

- **没有转储的崩溃无法自动分析。** 这是现场缺失的问题，不是工具的问题。想让下次
  硬挂死留下证据，需要配合"手动崩溃触发"（`CrashOnCtrlScroll`）。
- **默认的小内存转储信息量很低。** 检查 `CrashDumpEnabled`：`3` 是只生成 256KB
  的小转储，改成 `7`（自动 / 内核级）才有分析价值。
- **既没有 41 也没有 1001 的崩溃看不见**（开机早期就挂、或纯断电）。
- **应用层（用户态）崩溃不覆盖**，只处理内核层。
- **`LiveKernelReports` 读不到**（ACL 限制）。
- **停止码词典只覆盖常见的几十条**，没见过的码会显示原始代码和参数，但标为"未知"。
- **崩溃超过 14 天会自动跳过异常扫描** —— 那时事件日志多半已轮转，硬扫只会出假阳性。
- 只支持中文输出，且只在 Windows 上工作。

**它负责"把证据摆出来"，不负责"下结论"。** 报告里的"非常规"只表示不常出现，
不等于它就是原因。
